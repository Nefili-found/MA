# 多智能体论文「上下文调用工具」汇总文档

> 编制目的：收集本工作区 6 篇论文中，智能体用于**获取 / 调用上下文**（代码上下文、知识上下文、历史漏洞模式、外部执行结果等）的工具、函数与检索机制，形成可复用的参考文档。
> 编制日期：2026-10-06
> 来源论文：见第 1 节

---

## 0. 概念界定

本文档中的「上下文调用工具」指多智能体系统中，智能体为弥补单次推理输入信息不足、主动**拉取额外上下文**所依赖的手段，包括：

- **显式工具调用（Tool-calling）**：智能体自主决定调用某函数获取结构化上下文（如调用关系、函数体）。
- **检索增强（RAG）**：将外部知识库向量化，按相似度检索最相关条目注入 prompt。
- **外部执行（Execution）**：调用解释器 / 测试器获得运行期上下文。
- **内部上下文管理**：通过讨论历史压缩、回放缓冲等机制在系统内部维护/复用上下文（无外部工具）。

## 2. 逐篇工具详述

### 2.1 MAVUL（P1）

**核心思想**：漏洞分析智能体（Analyst Agent）像人类安全分析师一样，在推理不足时自主决定调用工具追踪跨过程上下文；另有架构师与评估智能体协作精化。

#### 2.1.1 显式工具集（Tool Set）—— 由 Analyst Agent 自主调用

| 工具名 | 输入 | 输出（Observation） | 功能 |
|--------|------|---------------------|------|
| `get_callers` | 目标函数 | `callers`（调用者列表） | 返回当前目标函数的所有调用者，用于追踪参数数据流（如输入校验漏洞） |
| `get_callees` | 目标函数 | `callees`（被调用者列表） | 返回当前目标函数的所有被调用者，用于检查资源释放/指针使用（如空指针解引用） |
| `get_function_body` | 定位到的函数 | `function_body`（函数实现） | 查看具体函数实现，理解跨过程依赖关系 |

- **调用机制**：Analyst Agent 在「Thinking → Acting（调用工具 / 检索记忆）→ Decision」循环中，自行判断是否需要调用工具以获取上下文；可多轮迭代。
- **预提取方式**：caller / callee / function_body 借助现有**静态分析工具**预先提取（论文标注为正交组件，可替换）。
- **可扩展性**：框架与任何知识检索技术正交（如 RAG），可接入更多漏洞相关数据库或工具。

#### 2.1.2 知识库（静态上下文源）

Analyst Agent 与 Evaluation Agent 共享以下知识库，作为推理的常驻上下文：

- **Code understanding**（代码理解能力，源自预训练）
- **CVE database**（CVE 漏洞库）
- **CWE list**（CWE 弱点分类清单）
- **Security principle**（安全原则）
- Evaluation Agent 额外包含 **Evaluation criteria**（评估标准）

#### 2.1.3 数据集附带的上下文元数据

MAVUL 所用的漏洞数据集包含丰富元数据，作为 ground-truth 上下文：`Binary label`、`CWE ID`、`CVE description`、`Commit message`、`Commit patch`。

### 2.2 ReasonVul（P2）

**核心思想**：三个专家智能体分别采用演绎、归纳、溯因推理并行分析代码，冲突时进入结构化辩论（Collaborative Debate）达成共识。上下文调用主要通过两条 RAG 检索管线完成。

#### 2.2.1 双 RAG 检索管线

| 智能体 | 知识库 K | 知识库来源 | 嵌入模型 | 检索策略 | 检索结果用途 |
|--------|----------|------------|----------|----------|--------------|
| **Deductive Agent**（演绎） | 安全规则库 K_D = {(desc_k, rule_k)} | SEI CERT C Coding Standard | **Jina-V3** | 余弦相似度，取 **Top-5** 描述 → 对应规则 | 将命中的高相关安全规则注入 prompt，自上而下检查违规 |
| **Inductive Agent**（归纳） | 历史漏洞库 K_I = {(c_vuln, c_fix)}，N = **6956** 个函数级漏洞-修复对 | ReposVul 数据集 | **Jina-V3** | 余弦相似度，**argmax** 最相似的历史样例 | 将最相似的「漏洞函数 + 修复函数」对作为 in-context example，自底向上模式匹配 |
| **Abductive Agent**（溯因） | **无外部 RAG** | — | — | — | 假设驱动逆向推理（由假想 adverse outcome 反推成因），仅用 LLM 内在推理，未接入外部知识库 |

- **离线索引阶段**：对知识库文本用 Jina-V3 编码为高维向量建立检索索引。
- **在线检索阶段**：将待分析代码片段 X 同样编码为 E(X)，与索引计算余弦相似度 `cos_sim(E(X), E(desc_k))` / `cos_sim(E(X), E(c_vuln))`，取最相关条目。
- **两条知识库**（图 3 标注）：`Vulnerability Code Knowledge Base` 与 `Security Rules Knowledge Base`，分别对应归纳与演绎管线。

> 注：ReasonVul 自身不直接定义 tool-calling 接口，而是以「RAG 检索 + 知识库」作为上下文注入手段；其对比基线 Vul-RAG 即典型的归纳式 RAG 方法。

### 2.3 COMAS（P3）

**核心思想**：通过智能体间「提出方案 → 评估 → 打分」的交互产生内在奖励，实现无需外部监督的多智能体自演化（RL 训练）。**该系统未设计显式外部工具调用**，上下文完全在系统内部维护。

#### 2.3.1 内部上下文管理机制

| 机制 | 符号 | 说明 |
|------|------|------|
| 完整输入上下文 | `p` | 随交互类型变化的输入 prompt，作为策略 `o = π_θ(p)` 的输入 |
| 讨论历史 | `h_q` | 每个问题 q 的累计讨论轨迹；**压缩到最近 κ 轮**以避免超出上下文长度限制 |
| 交互模式 | Solution / Evaluation / Scoring | 智能体基于 `(q, h_q)` 生成方案、基于 `(q, h_q, s_i)` 评估、基于 `(q, s_i, e_i,j)` 打分 |
| 回放缓冲 | `D_k = {(p, o, r(o))}` | 收集每个智能体作为 solver/evaluator/scorer 的交互样本，p 为上下文、o 为输出、r(o) 为奖励，供 REINFORCE++ 策略优化 |

- **上下文注入途径**：每轮生成的方案 `s_i` 与评估 `e_i,j` 追加进 `h_q`，从而「丰富后续轮次的上下文」。
- **训练数据来源**（作为初始问题上下文）：WebInstruct-verified、coding、science 类基准数据集。
- **结论**：COMAS 的「上下文」是**对话/讨论历史与回放样本**，而非外部检索工具，属于内部上下文管理范式。

### 2.4 MASS（P4）

**核心思想**：Multi-Agent System Search，将 MAS 设计自动搜索为「模块级提示优化 → 工作流拓扑优化 → 工作流级提示优化」三阶段。在搜索空间中把「上下文调用」抽象为可优化的构建块。

#### 2.4.1 Tool-use 构建块（上下文调用核心）

- **定义**：使智能体能借助工具获取外部信息，论文明确列举两类：
  1. **Retriever for RAG**（检索器，用于检索增强生成）
  2. **Executor with test cases / code execute**（代码执行器，在编码任务中执行测试用例）
- **优化形式**：Tool-use 作为可优化的二元「插入」决策 `N_T ∈ {0, 1}`，由预测器决定是否在智能体旁插入工具调用。
- **定位**：与 Aggregate / Reflect / Debate / Summarize 并列的五大构建块之一。

#### 2.4.2 其他与上下文相关的构建块

| 构建块 | 与上下文的关系 |
|--------|----------------|
| **Summarize**（自定义智能体） | 引入 summarize 智能体提升**长上下文能力**，Ns 定义信息抽象的轮数 |
| Aggregate | 多智能体并行多样化预测后聚合（多数投票 / 自一致性），不改变上下文来源 |
| Reflect | 智能体作为验证者基于前序预测提供批评与改进建议，迭代精炼 |
| Debate | 辩论智能体收集其他所有智能体意见并更新响应 |

> 注：MASS 将上述工具/机制作为**搜索空间中的可配置维度**，而非固定实现；论文未绑定具体检索器或执行器实例，而是给出抽象接口（RAG retriever、code executor）。

### 2.5 Wang 等（P5）

**核心思想**：基于博弈论提出「3+1」异构多智能体架构——3 个云端专家智能体（DeepSeek-V3）+ 1 个本地验证器（Qwen3-8B），以低成本实现高覆盖的漏洞检测。**该系统未设计显式工具调用（tool-calling）**，上下文靠输入代码、角色化提示与知识交叉引用获取。

#### 2.5.1 智能体与上下文来源

| 智能体 | 模型 / 部署 | 角色与上下文来源 |
|--------|------------|------------------|
| Code Analyst (a1) | DeepSeek-V3（云端 API） | 分析数据流、控制流、漏洞入口点、内存操作；上下文 = 输入代码 + 结构语义理解 |
| Security Expert (a2) | DeepSeek-V3（云端 API） | CWE 分类匹配、已知漏洞模式、严重度评估；上下文 = 输入代码 + **CWE 分类法（内部知识）** |
| Debug Expert (a3) | DeepSeek-V3（云端 API） | 错误处理、边界条件、未定义行为；上下文 = 输入代码 + 行为语义理解 |
| Verifier | Qwen3-8B（本地 GPU，零边际成本） | 对抗式验证；**接收原始代码 + 全部 3 份专家报告**，交叉引用（cross-referencing）后可推翻专家共识 |

- **调用机制**：3 个专家以专用 system prompt 并行运行（Python asyncio），各输出结构化报告 `VULNERABILITY_FOUND / CWE_IDs / SEVERITY / EVIDENCE / CONFIDENCE`；验证器在 Layer 2 进行对抗式验证博弈。
- **上下文注入途径**：专家仅获得「原始代码 + 角色提示」；验证器获得「原始代码 + 全部专家报告」，通过信息汇总实现跨视角核对。**无 RAG、无静态分析工具调用、无外部检索**。

#### 2.5.2 外部工具（仅作评测基线，非智能体调用）

- **Cppcheck 2.13.0**：开源静态分析工具（全检查开启），作为检测准确率/误报率对比的 baseline，**不被任何智能体调用**。
- 数据集：NIST Juliet Test Suite v1.3（64,295 C/C++ 用例，118 类 CWE）。

> 注：Wang 的「上下文调用」属于**内部/输入型**——靠输入代码与 CWE 分类知识，无动态检索工具；这使其成本低（本地验证器零边际成本），但缺乏跨过程/跨仓库上下文追踪能力，与 MAVUL、MAVM 形成对照。

### 2.6 Zheng 等 — MAVM（P6）

**核心思想**：首个面向「反复漏洞（recurring vulnerability）」端到端管理的多智能体框架，覆盖「漏洞知识库构建 → 检测 → 确认 → 修复 → 验证」全流程。为克服 LLM 缺乏仓库级上下文的问题，**显式设计了一组 context-retrieval tools**，使智能体可提取并推理仓库级信息。

#### 2.6.1 上下文检索工具（Context-Retrieval Tools）—— 4 个

论文基于 **ripgrep [19]** 与 **Tree-sitter [20]** 实现，共 **4 个工具**，分别用于从「原始漏洞仓库（source）」与「目标仓库（target）」检索函数与结构体定义：

| 工具 | 底层实现 | 检索目标 | 用途 |
|------|----------|----------|------|
| 检索函数定义（目标仓库） | ripgrep + Tree-sitter | target repo 中某函数的完整定义 | 供 Analyzing Agent 检查可疑函数实现 |
| 检索函数定义（源仓库） | ripgrep + Tree-sitter | source repo（原始漏洞）中对应函数定义 | 与 target 比对，判断实现是否一致 |
| 检索结构体定义（目标仓库） | ripgrep + Tree-sitter | target repo 中某 struct 的定义 | 定位相关数据结构（如未初始化字段） |
| 检索结构体定义（源仓库） | ripgrep + Tree-sitter | source repo 中对应 struct 定义 | 与 target 比对，识别误报（如字段已全部初始化） |

- **调用场景**：
  - **确认阶段（Confirmation）**：Analyzing Agent 借助这些工具从两仓库获取函数/结构体定义，判断目标代码是否真正复现原始漏洞（如图 5 案例：靠「按名称检索结构体定义」工具确认 `kvaser_cmd_simple` 字段均已初始化，从而识别为误报）。
  - **修复阶段（Repair）**：Consistency-Check Agent 用专用分析工具检查历史补丁涉及函数在源/目标仓库间的一致性（函数名、参数）；当所需函数在目标仓库缺失时，Fixing Agent 借助上述上下文工具在目标仓库内搜索语义相似替代函数。
- **设计要点**：若目标仓库中某函数实现与源漏洞仓库**完全相同**，则判定该因素不影响漏洞发生（直接排除），体现「仓库级上下文驱动决策」。

#### 2.6.2 漏洞知识库（VKB）构建工具 / 信息源

VKB 是 MAVM 的常驻领域上下文，由以下来源构建（三类组件：基础信息 + 漏洞分析报告 + 分析要点）：

| 信息 / 工具 | 来源 | 说明 |
|-------------|------|------|
| CVE 描述 + CWE 类别 | **NVD**（由 CVE ID 检索） | 基础信息 |
| 仓库名 / 文件路径 / 漏洞函数代码 / 补丁内容 / commit message | **Git Commit URL** | 基础信息 |
| 漏洞分析报告 | **GPT-4o**（基于多视角模板自动生成） | 含根因分析、触发链分析、补丁分析三维度 |
| 分析要点（Analysis Points） | **GPT-4o**（从报告蒸馏） | 可操作诊断启发式（如 API 误用模式、边界错误），供 Porting Agent 映射到新上下文 |

#### 2.6.3 检测器（静态检测工具，可插拔）

| 工具 | 原理 | 角色 |
|------|------|------|
| **ReDeBug [4]** | 基于语法的模式匹配，快速查找未打补丁的漏洞代码克隆 | 核心检测器（可插拔） |
| **Tan 等哈希方法 [5]** | 哈希值接近已披露漏洞函数的疑似漏洞函数识别 | 核心检测器（可插拔），可调低检索阈值提升覆盖 |

- 两者结果取**并集**作为检测阶段输出，最大化覆盖、降低漏报。
- 在验证阶段（Patch Validation）**再次调用原检测器**判断补丁后代码是否仍含漏洞。

#### 2.6.4 智能体流水线（7 个角色，均依赖上述上下文工具）

`VKB` → `Detector`（ReDeBug+哈希）→ `Porting Agent`（移植分析要点）→ `Analyzing Agent`（确认漏洞）→ `Consistency-Check Agent`（跨仓一致性）→ `Fixing Agent`（修复）→ `Validation Agent`（验证）。其中 Analyzing / Consistency-Check / Fixing / Validation 在推理时均会调用 2.6.1 的 4 个上下文检索工具获取仓库级上下文。

## 4. 可复用的上下文调用模式总结

按「上下文来源」归类，本批论文暴露出 5 类可迁移模式：

1. **代码级上下文（过程依赖 / 调用图）** — MAVUL 的 `get_callers / get_callees / get_function_body`：静态分析预提取调用图，智能体按需跨过程追踪，适合需要数据流/控制流理解的漏洞（输入校验、空指针等）。
2. **代码级上下文（仓库级 / 跨仓定义）** — MAVM 的 4 个 ripgrep + Tree-sitter 检索工具：直接检索函数/结构体在源与目标仓库的定义，支撑跨仓库一致性判断与误报识别，适合「反复漏洞」这类需跨项目比对的场景（比 MAVUL 的调用图更进一步到跨仓粒度）。
3. **知识级上下文（RAG / 知识库）** — ReasonVul + MASS + MAVM：将规则库/历史漏洞库/VKB 向量化（Jina-V3 等）或结构化（VKB 由 NVD+Git+GPT-4o 构建）后注入；可覆盖「权威性规则」「历史相似模式」「深度根因分析」三种语义。
4. **执行级上下文（运行反馈）** — MASS 的 code executor：让智能体通过执行测试用例获得真实运行信号，弥补纯静态/语义推理的不足。
5. **内部上下文管理（无外部工具）** — COMAS 的讨论历史压缩 + 回放缓冲，以及 Wang 的「输入代码 + CWE 知识 + 验证器交叉引用专家报告」：在自演化/低成本场景下以最小开销复用上下文，但缺乏跨过程/跨仓追踪能力。

**设计启示**：一个鲁棒的多智能体漏洞检测/管理系统往往会**组合**上述模式——以 MAVUL/MAVM 式代码工具获取过程与仓库级上下文，以 ReasonVul/MAVM 式知识库注入领域知识与历史根因，并辅以 MASS 式执行验证与长上下文摘要；Wang 则证明「无显式工具 + 异构模型 + 本地验证器」可在成本约束下取得实用效果。
