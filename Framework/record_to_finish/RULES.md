# record_to_finish/ 文件夹规则

> 本文件夹用于记录**测试过程中遇到的失败**及其**原因**，并附**可改进建议**，
> 目标是把项目代码逐步跑通。每跑一次测试、每暴露一个问题，就落一份记录。
>
> **「失败」的定义（满足以下任一条即为失败，都必须记录）：**
> 1. **运行失败**：报错 / 抛异常 / 非零退出码 / 中途中断。
> 2. **未按需求达成**：程序能跑通，但**结果不符合需求 / 预期**——例如降级模式、
>    结果为空（0 findings）、字段缺失、输出与预期不符、未完成指定功能等。
>
> 换言之，**即使退出码为 0，只要没达到本次测试的预期目标，也按失败记录。**
> 每条记录都应在「失败原因」中写明**期望结果**与**实际结果**的差距。

---

## 1. 目录结构

```
record_to_finish/
├── RULES.md              # 本文件：规则 + 记录清单索引表
├── YYYY-MM-DD/           # 每天一个文件夹，存放当天全部测试记录
│   └── YYYY-MM-DD_NN.md  # 一次测试一个记录文件（NN 为当天两位序号）
└── resolved/             # 已解决的记录移入此目录，保留历史
```

---

## 2. 命名规则

- **同一天的测试集中放在一个以日期命名的文件夹里**：`YYYY-MM-DD/`
  （如 `2026-10-03/`）；当天没有记录就不建文件夹。
- 记录文件名用**测试时间**表示：`YYYY-MM-DD_NN.md`
  （如 `2026-10-03/2026-10-03_01.md`）；`NN` 为当天测试的两位序号，从 `01` 起递增。
- 规则文件名固定为 `RULES.md`（本文件，位于 `record_to_finish/` 根下）。

---

## 3. 记录文件内容（固定三部分）

每个记录文件按以下模板填写：

```markdown
# 测试记录 YYYY-MM-DD

## 失败原因
- 现象：            # 报错信息 / 异常表现（原文粘贴；无报错则填「无报错，但结果未达预期」）
- 复现步骤：        # 执行的命令、输入文件、配置等
- 期望结果：        # 按需求本应得到什么
- 实际结果：        # 实际得到什么（含退出码、关键日志）
- 定位：            # 出错文件:行号，如 agents/__init__.py:50

## 改进建议
- （可留空，后续补填）

## 解决措施
- （可留空，后续补填；解决后建议同时记录验证方式）
```

- **失败原因**：测试时即填写；须体现「期望结果 vs 实际结果」的差距。
- **改进建议 / 解决措施**：允许**留空**，在后续分析或修复时再补填。

## 5. 维护规则

1. **新增**：只要一次测试构成**失败**（见开头定义：**运行失败** *或* **未按需求达成**），
   就把记录写进**当天的日期文件夹** `record_to_finish/YYYY-MM-DD/`
   （文件夹不存在则新建），文件名为 `YYYY-MM-DD_NN.md`，
   按第 3 节模板填写「失败原因」（含期望结果 / 实际结果）。
2. **更新索引**：新增记录后，**立即**在第 4 节索引表追加一行，状态填「未解决」。
3. **解决**：修复后——填好记录文件的「改进建议 / 解决措施」→ 把该文件移入 `resolved/`
   → 索引表「状态」改为「已解决」，「文件」列更新为 `resolved/YYYY-MM-DD_NN.md`。
4. **留痕**：记录文件原则上只增不改；内容有补充时直接在原文件对应小节追加，不覆盖历史结论。
