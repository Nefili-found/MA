# 提示词对比分析：our prompt（3 视角） vs VulAgent（2025） vs AAMAS-3+1（2026）

> 比对对象：
> - **our prompt.txt**：自研 3 智能体提示词（Static Analyze / Behavior Analyze / Memory Layout），含 `assume`（漏洞假设）字段，强制 JSON 输出
> - **VulAgent**（arXiv:2509.11523）：动态路由 10 视角 + 4 后处理智能体，假设验证范式
> - **AAMAS 2026**（arXiv:2604.21282）：3 云端专家 + 1 本地对抗验证者（3+1）
>
> 结论先行：our prompt 在**角色解耦与抗幻觉约束**上设计得很到位，本质上是 VulAgent 三个常开基线智能体的清晰再实现、并自创了 `assume` 字段；但其**致命短板是没有"验证/聚合"阶段**——既不像 VulAgent 有 TriggerPlanner+AssumptionPruner+FinalValidator 的链式精化，也不像 AAMAS 有 Adversarial Verifier 做对抗校验，因此 precision 提升机制缺失。

---

## 一、角色映射关系

| our prompt 视角 | VulAgent 对应 | AAMAS 对应 | 重合度 |
|---|---|---|---|
| **Static Analyze**（AST/CFG/DFA、污点传播、不安全 API、空指针、未初始化、硬编码密钥） | StaticAnalyzerAgent（静态模式） | Code Analyst（结构/数据流）+ Security Expert 部分 | 高 |
| **Behavior Analyze**（执行分支、异常路径、权限提升、恶意输入触发的异常分支） | BehaviorAnalyzerAgent（控制/数据流、缺失检查） | Debug Expert（边界/错误处理/未定义行为） | 高 |
| **Memory Layout**（栈/堆/结构体、溢出、UAF、越界读写、对齐、相邻对象篡改） | MemoryLayoutAgent（指针算术/缓冲区） | Security Expert 内存安全部分（CWE-415/416/787/122/121） | 高 |

**关键发现**：our prompt 的三个视角与 VulAgent 的 **3 个 always-on 基线智能体（B = {Static, Behavior, MemoryLayout}）几乎一一对应**，可以看作是对 VulAgent 基线 trio 的"加约束重写"。VulAgent 在此基础上还动态激活另外 7 个专用视角（FormatString / FilePermission / AuthFlow / CryptoConfig / Concurrency / ErrorHandling / CodeInjection），并加了一层 MetaAgent 路由；our prompt 缺失这些，存在覆盖盲区。

## 二、逐维度对比表

| 维度 | our prompt（3 视角） | VulAgent | AAMAS 3+1 |
|---|---|---|---|
| 视角数量 | 固定 3 | 动态 10（基线 3 常开） | 固定 3 + 验证者 1 |
| 视角划分依据 | 分析能力（静态/行为/内存） | CWE 语义族 | 分析能力 + 对抗审计 |
| 是否含验证/聚合层 | **无** | 有 4 层（聚合+假设+剪枝+校验） | 有 1 层（对抗验证者）+ 多数投票 |
| 漏洞假设机制 | `assume` 字段（仅列举，不校验） | 假设 A + 触发路径 P，下游两阶段验证 | 无显式假设，验证者查"遗漏/矛盾" |
| CWE 标准化 | **无**（vuln_type 自由文本） | 有（CWE 字段） | 有（Security Expert 硬编码 14 个 CWE） |
| 严重性/置信度 | **无** | 末端 cwe_list | SEVERITY + CONFIDENCE |
| 输出格式 | 严格 JSON | 严格 JSON | 半结构化字段（伪 JSON） |
| 行号引用 | 输出含 code_location | 全流程行号贯穿 | 未强调（输入仅代码片段） |
| 抗幻觉约束 | 强（"空数组/不编造"，且禁运行时模拟） | 中（上游求召回，靠下游剪枝） | 中（验证者查证据/幻觉） |
| 工具上下文 | 让 LLM "基于 AST/CFG/DFA"（**靠 LLM 推理**） | 用 Joern 真实抽取 CFG/数据依赖/调用图 | 仅原始代码（+ Juliet include） |
| 跨视角去重 | **无**（3 份独立报告） | Aggregator 按 CWE+行区间合并 | CWE 池并集聚合 |

## 三、our prompt 的优点（含原因）

### 1. 角色边界约束极其明确 —— 这是最值得保留的设计
每个视角都用 `Constraints` 显式写了"不要越界"：Static 禁运行时模拟、禁内存布局；Behavior 禁内存细节、禁仅凭 AST 下结论；Memory 禁业务逻辑/纯语法污点。
- **原因**：多智能体最容易产出互相打架的重复报告。our prompt 用硬约束把三个视角切成互不重叠的切片，天然降低了输出冲突——这个设计思路比 AAMAS 仅用"视角名称"切分更稳，也比 VulAgent 靠"路由描述"切分更可执行。

### 2. 自创 `assume` 字段抓住了"漏洞判定"的本质
`assume` 要求描述"触发前置条件 / 输入条件 / 后果"，这其实就是 VulAgent 中"假设 A"的雏形。
- **原因**：把"这里有个可疑点"升级为"在什么条件下它会真正被触发"，迫使模型从'语法可疑'迈向'可达性'，直接针对 LLM 漏洞检测的核心误报来源（把理论缺陷当真实攻击面）。这是 our prompt 相对纯 baseline 最有价值的一点创新。

### 3. 强制 JSON + 禁额外解释 —— token 高效、易解析
- **原因**：与两篇论文的 JSON 契约一致，便于下游程序化聚合；`temperature=0` 类确定性设定下最省 token。our prompt 还要求"若无疑险则空数组、不得编造"，抗 fabrication 意识比 VulAgent 上游（显式求最大召回、允许误报）更强。

### 4. Static 视角禁止"模拟运行时" —— 方法论更诚实
- **原因**：AST/数据流层面的静态特征可以靠模型判断；但"运行时行为"本就超出单函数静态分析能力。明确划界，避免模型用想象的执行轨迹支撑结论，正好规避了 VulAgent 案例研究里"把不可达路径当漏洞"的翻车模式。

## 四、our prompt 的不足（含原因与风险）

### 1. 【最严重】没有验证 / 聚合层 → precision 无保障
- **表现**：3 个视角各写一份 JSON，彼此不交叉、不裁决、不合并。VulAgent 用 Aggregator→TriggerPlanner→AssumptionPruner→FinalValidator 四层把召回与精确解耦；AAMAS 用 Adversarial Verifier + 多数投票兜底。
- **原因/风险**：our prompt 把"高召回（assume 尽量列）"和"精确（只报真的）"压在同一个模型同一次输出里，模型既要敢报又要克制，自相矛盾。实验上 AAMAS 证明一个本地验证者单枪匹马把 precision 从 52.6% 拉到 62.9%（+10.3pp，且 0 个真阳性被误杀）。our prompt 没有这个安全阀，FPR 会偏高，且 3 份不一致报告无法裁决。

### 2. `assume` 只生成、不验证 —— 假设仍是"裸假设"
- **表现**：our prompt 让模型列出 assume，但**没有** VulAgent 的 AssumptionPruner（判定 plausible/contradicted/unknown）和 FinalValidator（Path_validity）。
- **原因/风险**：assume 一旦写错（如"input 可控"其实不可控）就永远错下去，没有二次核验。这正是 our prompt 与 VulAgent 假设机制的本质差距——你有"提出假设"的形式，缺"验证假设"的纪律。

### 3. 无 CWE 标准化、无 SEVERITY/CONFIDENCE
- **表现**：vuln_type 是自由文本；没有 CWE 编号、严重性、置信度字段。
- **原因/风险**：① 无法做层次化 CWE 匹配（AAMAS 用 CWE-121/122→父类 CWE-120 的等价类，把 match rate 拉到 100%），评估结果会失真；② 没有置信度就无法设阈值、无法排序、无法让下游只采信高置信条目；③ 人工复核成本高。

### 4. 覆盖率缺口：缺 7 类语义视角
- **表现**：没有格式化字符串、文件/权限、认证流、密码学配置、并发、错误处理、代码注入的专用视角。
- **原因/风险**：这几类恰恰是真实漏洞高频区（CWE-78 命令注入、CWE-134 格式化串、CWE-190 整数溢出等）。VulAgent 把它们设为可路由激活；AAMAS 至少用 Security Expert 的硬编码 CWE 清单覆盖。our prompt 完全没覆盖，会系统性漏报这几类。

### 5. "基于 AST/CFG/DFA" 是伪指令 —— 让 LLM 做它做不好的事
- **表现**：Static 视角要求"基于 CFG/DFA 扫描并定位污点传播链"。
- **原因/风险**：LLM 内部并不真正构建 CFG/数据流图，长函数上会臆造边。**VulAgent/AAMAS 的做法是先用真实静态工具（Joern）抽取图，再喂给 LLM**。our prompt 指望模型"脑补"CFG，既不可靠也不可复现。建议要么接真实工具产出 CFG 作为上下文，要么把这条改成"基于可见的控制流结构推断"。

### 6. 无跨视角去重/冲突裁决
- **表现**：同一处 buffer overflow 可能被 Static（不安全 API）和 Memory（越界写）各报一次。
- **原因/风险**：VulAgent 用 Aggregator 按 CWE+行区间合并、记 source_agents；our prompt 没有，下游会收到重复项，且无法知道"几个视角都同意"（AAMAS 用 AGREEMENT_LEVEL 量化一致性）。

### 7. 草案痕迹
- `assume` 上方的"（考虑是否需要）"说明输出格式尚未定稿；字段名中英混排（code_location / vuln_type / evidence / agent_type 是英文键，但值示例含中文"代码位置/行号"）。属工程整洁度问题，不影响方法。

## 六、改进建议（按性价比排序）

1. **加一层验证者（最高性价比，直接抄 AAMAS）**：新增第 4 个视角"Verifier"，输入=3 份报告+源码，输出 DECISION(ACCEPT/CHALLENGE/REJECT)+FINAL_VULNERABILITY+REASONING。本地小模型即可，零边际成本。预计 precision +10pp 量级。
2. **给 assume 加验证纪律（抄 VulAgent）**：在 Behavior/Static 之后加 TriggerPlanner（assume→触发路径+前置条件）和 AssumptionPruner（逐条标 plausible/contradicted/unknown），过滤不可达假设。
3. **CWE 字段化 + 严重性/置信度**：把 vuln_type 改成 `cwe_id` + `severity` + `confidence`，即可算层次化匹配率、可设阈值。
4. **补 7 类语义视角或合并进 Security-CWE 清单**：至少加 FormatString / Injection / Concurrency / Auth / Crypto / ErrorHandling 视角，或学 AAMAS 在某一视角硬编码 CWE 清单覆盖。
5. **真实 CFG/数据依赖喂入**：用 Joern/CodeQL 抽图，作为 `{code_context}` 注入，删掉"LLM 基于 CFG"的伪指令。
6. **跨视角去重**：加 Aggregator，按 CWE+行区间合并，记录 source_agents 与 AGREEMENT_LEVEL。

---

## 七、一句话结论

our prompt 是一份**结构清晰、角色边界硬、且自带抗幻觉与假设意识的优秀"检测端"草稿——但它目前只有 VulAgent 的 3 个基线智能体，缺了 VulAgent 的验证流水线和 AAMAS 的对抗验证者**，因此"敢报"有了、"能筛真"没有。补上"验证层 + CWE 标准化 + 真实图上下文"三件事，就能从一份好草稿升级为可评估、低误报的多智能体检测框架。

### 附：三套提示词"假设/假设校验"机制对照（核心差异点）

| 机制 | our prompt | VulAgent | AAMAS |
|---|---|---|---|
| 提出假设 | `assume` 列表 | 假设 A + 触发路径 P（TriggerPlanner） | 无显式；专家报告即主张 |
| 校验假设 | **无** | AssumptionPruner 标 plausible/contradicted/unknown | Verifier 查"证据/遗漏/矛盾" |
| 路径可达性 | Behavior 视角隐含 | TriggerPlanner 显式回溯 attacker-controlled source→sink | 无显式路径 |
| 最终裁决 | 无（3 份并列） | FinalValidator 判 Path_validity，给 cwe_list | Verifier DECISION 可覆盖多数投票 |
